### Lime r5 最窄修复输入合同

当前 `listCanonicalSessionOverviews` 遍历 section catalog 与 null，却将 requestedLimit 用作所有 scope 的 collapsed 总预算并最终 slice；随后 Sidebar 才拆分 Pinned/custom/Recents。这会让 Recents 的足额被其它组消耗。它是可确认的 Lime 输入组合问题，无须改通用 limit 语义，也不能将修复冒称成 Codex 原样的三类 RPC 实现。

Root 选定的最窄实现是让既有 session gateway 暴露 canonical `thread/list` page，保留真实 `nextCursor`，由 Sidebar source 在自己的 scope 内推进 cursor 到相关组预算或来源结束。通用 `listCanonicalSessionOverviews` 的总 limit 语义保持原合同；不新增内部 sectionId option 来承载一套混合 list/page 语义，不保留 prefix 重取或 array.length 近似 hasMore 的临时路径。

输入应显式携带当前 canonical page 已有的 section/filter/cwd/archive/sort 与 cursor，输出为同一 overview 投影和服务端 nextCursor；没有新 RPC/backend。cursor、more、pending 和迟到身份绑定该实际 source scope。Pinned/custom/Recents 是否各用 null 或具体 section，按 Lime 当前 protocol/store 分区选择；这是 Lime 协议 scope 适配，不声称 Codex 按 section 拆 RPC。客户端还须过滤 pinned/custom、cwd/workspace 或去重时，在同一 source 沿 nextCursor 继续到相关组足额、真实 cursor 耗尽或明确失败，不能被其它组数量截止；重复 cursor 要停止并显式处理，scope变化须丢弃旧页。

Lime 当前 `hasMore` 由同一 source 未消费的服务端 nextCursor 决定，不能用跨组 globalSessionCount 或数组长度替代。参考 catalog 尚未完成物化时的 source-completeness 还有额外状态；未迁入的这部分仍是 gap，不伪造一个“完整对齐”布尔值。不要另建 sidebar backend、第二线程投影/持久化、改通用 limit 为“每section都limit”的隐式新语义，或创建只有同名的空预取/包装层。

已证原包明文方法名有 `listPage`、`readItem`、`ensurePage`、`loadMore`、`getPageState`、`getEntries`、`getListKey`、`listAllThreads`、`listRecentThreads`。`ALs/l5/f7t/Vor/ecr/lis/uis` 是该构建压缩局部符号，不能拿来命名 Lime 类型/类；原始 TS 类名和目录未恢复。完整 custom-section engine/host 参数、reader/service bridge 的所有字段、部署 flags 与真实参考运行仍未知。
